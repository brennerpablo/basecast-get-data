# Decisions — basecast-get-data

One line per decision: date, decision, reason. This log also holds decisions that affect more than one repo.

- 2026-09-26 — GCP project `basecast-509812`, everything in `us-central1`; setup scripts live in `basecast-airflow/deploy/gcp/` (branch `infra/gcp`). — The ERCOT API blocks non-US access; one place for infra keeps the three repos from drifting.
- 2026-09-26 — Cloud SQL Postgres 17 (`basecast-pg`, Enterprise edition, db-f1-micro, zonal, 10 GB SSD, 7 daily backups, no PITR) holds Airflow's metadata (`airflow`) and operational data that does not need Parquet/BigQuery (`basecast`). Reverses "no Cloud SQL" from KICKOFF §2. — Asked by the user; db-f1-micro is the cheapest tier (US$ 7.67/month) and SSD adds only US$ 0.80/month over HDD, whose IOPS are too low at 10 GB for Airflow.
- 2026-09-26 — Postgres is reached only through the Cloud SQL connectors (connector enforcement on, no authorized networks); roles `airflow`, `basecast_writer` (pipelines) and `basecast_reader` (this API, `SELECT` only) are created in SQL, not through the API. — API-created users join cloudsqlsuperuser; the API must never be able to write.
- 2026-09-26 — db-f1-micro allows 25 connections: every client keeps a small pool (Airflow: pool 2 + overflow 3 per process; this API should use 2–3). — Airflow's scheduler, API server and DAG processor each hold their own pool.
- 2026-09-26 — This API deploys to a Cloud Run service (min 0 instances, service account `get-data-run`), not a Cloud Function. — Same price and free tier (Cloud Run functions run on Cloud Run), but the Python Functions Framework is Flask-based and does not serve FastAPI (ASGI).
- 2026-09-26 — Cloud Run allows unauthenticated invocation and the API checks the `API_TOKEN` bearer (secret `get-data-api-token`). — Google IAM auth would force the Vercel BFF to mint ID tokens with a service account key.
- 2026-09-26 — Airflow VM `basecast-airflow`: e2-medium (4 GB, US$ 24.46/month), Debian 12, 30 GB pd-standard, Docker Compose with LocalExecutor, no triggerer; no public ports (SSH through IAP, UI through an SSH tunnel), ephemeral external IP for outbound calls. — Airflow 3.3 asks for at least 4 GB; Cloud NAT would cost more than the IP.
- 2026-09-26 — Budget alert of R$ 250/month on the project (50/90/100%). — The billing account is in BRL; expected spend is ~US$ 35–39/month running 24/7.
- 2026-09-26 — The app (`basecast-app`) keeps its login users in Cloud SQL database `basecast`, schema `app` (Prisma, connects as `postgres`). Pipelines and the API never create tables there; `basecast_reader` has no grant on it. — Keeps password hashes out of the API's reach and the app's `prisma db push` away from the pipelines' tables in `public`.
- 2026-09-26 — Pipelines write processed tables to Postgres `basecast`, schema `public` (PostGIS enabled), as `basecast_writer`; the large datasets live in BigQuery `basecast-509812.basecast` (partitioned by month), with their Parquet in `gs://basecast-509812-lake/parquet/`. `get-data-run` got `roles/bigquery.dataViewer` and `roles/bigquery.jobUser`. — The user's split: Postgres for what the API reads, BigQuery for the big series.
- 2026-09-26 — `etl_run` is a Postgres table in `basecast` (columns: run_id, source, stage raw|process, dag_id, task_id, airflow_run_id, try_number, started_at, finished_at, duration_s, status running|success|partial|failed, rows, files, files_skipped, bytes, error, events jsonb, params jsonb); `lake_processed` records what each dataset has parsed. — Source of `/pipeline/runs` and `/sources` (data contract §6).
- 2026-09-26 — Official forecasts share one long shape across LTLF, CDR and manual figures (vintage, vintage_date, publisher, product, target_year, target_month, season, region_type, region_id, metric, scenario, value, unit + provenance), unioned into `official_forecasts`. — Feeds the backtest resource without per-source logic in the API.
- 2026-09-26 — basecast-airflow and basecast-get-data deploy through GitHub Actions on every push to `main`, as in fundsys (VM over IAP; Cloud Run from source). Work lands straight on `main`, no PRs. Setup: `basecast-airflow/deploy/gcp/06-github-actions.sh`. — Asked by the user: same flow as fundsys; deploys come off `main`.
- 2026-09-26 — GitHub Actions authenticate through Workload Identity pool `github-pool`, which only accepts `brennerpablo/basecast-airflow` and `brennerpablo/basecast-get-data` on `refs/heads/main`; one deploy service account per repo (`airflow-deploy`: OS Login admin and IAP tunnel only; `get-data-deploy`: Cloud Run, Cloud Build, Artifact Registry). — No service account keys; fundsys scopes by org owner, but `brennerpablo` is a personal account with unrelated repos.
- 2026-09-26 — The Airflow VM's `.env` comes from GitHub secret `AIRFLOW_ENV_FILE` and get-data's environment from `ENV_YAML`, as in fundsys; both were seeded from the VM's `.env` (keeping the Fernet key) and Secret Manager. — Asked by the user: same as fundsys. After seeding, the GitHub secret is the source of truth.
