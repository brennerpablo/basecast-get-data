# Decisions — basecast-get-data

One line per decision: date, decision, reason. This log also holds decisions that affect more than one repo.

- 2026-09-26 — GCP project `basecast-509812`, everything in `us-central1`; setup scripts live in `basecast-airflow/deploy/gcp/` (branch `infra/gcp`). — The ERCOT API blocks non-US access; one place for infra keeps the three repos from drifting.
- 2026-09-26 — Cloud SQL Postgres 17 (`basecast-pg`, Enterprise edition, db-f1-micro, zonal, 10 GB SSD, 7 daily backups, no PITR) holds Airflow's metadata (`airflow`) and operational data that does not need Parquet/BigQuery (`basecast`). Reverses "no Cloud SQL" from KICKOFF §2. — Asked by the user; db-f1-micro is the cheapest tier (US$ 7.67/month) and SSD adds only US$ 0.80/month over HDD, whose IOPS are too low at 10 GB for Airflow.
- 2026-09-26 — Postgres is reached only through the Cloud SQL connectors (connector enforcement on, no authorized networks); roles `airflow`, `basecast_writer` (pipelines) and `basecast_reader` (this API, `SELECT` only) are created in SQL, not through the API. — API-created users join cloudsqlsuperuser; the API must never be able to write.
- 2026-09-26 — db-f1-micro allows 25 connections: every client keeps a small pool (Airflow: pool 2 + overflow 3 per process; this API should use 2–3). — Airflow's scheduler, API server and DAG processor each hold their own pool.
- 2026-09-26 — This API deploys to a Cloud Run service (min 0 instances, service account `get-data-run`), not a Cloud Function. — Same price and free tier (Cloud Run functions run on Cloud Run), but the Python Functions Framework is Flask-based and does not serve FastAPI (ASGI).
- 2026-09-26 — Cloud Run allows unauthenticated invocation and the API checks the `API_TOKEN` bearer (secret `get-data-api-token`). — Google IAM auth would force the Vercel BFF to mint ID tokens with a service account key.
- 2026-09-26 — Airflow VM `basecast-airflow`: e2-medium (4 GB, US$ 24.46/month), Debian 12, 30 GB pd-standard, Docker Compose with LocalExecutor, no triggerer; no public ports (SSH through IAP, UI through an SSH tunnel), ephemeral external IP for outbound calls. — Airflow 3.3 asks for at least 4 GB; Cloud NAT would cost more than the IP.
- 2026-09-26 — Budget alert of R$ 250/month on the project (50/90/100%). — The billing account is in BRL; expected spend is ~US$ 35–39/month running 24/7.
- 2026-09-26 — The app (`basecast-app`) keeps its login users in Cloud SQL database `basecast`, schema `app` (Prisma, connects as `postgres`). Pipelines and the API never create tables there; `basecast_reader` has no grant on it. — Keeps password hashes out of the API's reach and the app's `prisma db push` away from the pipelines' tables in `public`.
- 2026-09-26 — Pipelines write processed tables to Postgres `basecast`, schema `public` (PostGIS enabled), as `basecast_writer`; the large datasets live in BigQuery `basecast-509812.basecast` (partitioned by month), with their Parquet in `gs://basecast-509812-lake/parquet/`. `get-data-run` got `roles/bigquery.dataViewer` and `roles/bigquery.jobUser`. — The user's split: Postgres for what the API reads, BigQuery for the big series.
- 2026-09-26 — `etl_run` is a Postgres table in `basecast` (columns: run_id, source, stage raw|process, dag_id, task_id, airflow_run_id, try_number, started_at, finished_at, duration_s, status running|success|partial|failed, rows, files, files_skipped, bytes, error, events jsonb, params jsonb); `lake_processed` records what each dataset has parsed. — Source of `/pipeline/runs` and `/sources` (data contract §6).
- 2026-09-26 — Official forecasts share one long shape across LTLF, CDR and manual figures (vintage, vintage_date, publisher, product, target_year, target_month, season, region_type, region_id, metric, scenario, value, unit + provenance), unioned into `official_forecasts`. — Feeds the backtest resource without per-source logic in the API.
- 2026-09-26 — basecast-airflow and basecast-get-data deploy through GitHub Actions on every push to `main`, as in fundsys (VM over IAP; Cloud Run from source). Work lands straight on `main`, no PRs. Setup: `basecast-airflow/deploy/gcp/06-github-actions.sh`. — Asked by the user: same flow as fundsys; deploys come off `main`.
- 2026-09-26 — GitHub Actions authenticate through Workload Identity pool `github-pool`, which only accepts `brennerpablo/basecast-airflow` and `brennerpablo/basecast-get-data` on `refs/heads/main`; one deploy service account per repo (`airflow-deploy`: OS Login admin and IAP tunnel only; `get-data-deploy`: Cloud Run, Cloud Build, Artifact Registry). — No service account keys; fundsys scopes by org owner, but `brennerpablo` is a personal account with unrelated repos.
- 2026-09-26 — The Airflow VM's `.env` comes from GitHub secret `AIRFLOW_ENV_FILE` and get-data's environment from `ENV_YAML`, as in fundsys; both were seeded from the VM's `.env` (keeping the Fernet key) and Secret Manager. — Asked by the user: same as fundsys. After seeding, the GitHub secret is the source of truth.
- 2026-09-26 — All three repos work on `main` only: no feature branches or worktrees, small commits pushed straight to `main`, checks before every push since `main` deploys (app → Vercel, this API → Cloud Run, airflow → the VM). — Asked by the user: parallel branches and worktrees across several sessions cost rebases and blocked handoffs.
- 2026-09-26 — Cloud SQL `basecast-pg` upgraded to db-custom-2-8192 (2 vCPU, 8 GB, 400 connections, ~US$ 3.33/day) for the hackathon; go back to db-f1-micro afterwards. Supersedes the tier (not the rest) of the Cloud SQL decision above. — PostGIS overlays of the initial load took 10+ minutes each on the shared core; the user approved a bigger instance for a few days.
- 2026-09-26 — One standardized log for the app, get-data and airflow: table `ops.log` (Postgres `basecast`, schema `ops`), same columns and event names in all three (data contract §7). The app reads it directly for its /ops screen, not through this API; the DDL is the app's Prisma model `OpsLog` and the grants are in the app's `prisma/ops-grants.sql`. This API will append through a role of its own that can only INSERT there, so `basecast_reader` stays SELECT-only. — Asked by the user; the monitoring screen must work while the API is down, and one table joins a click in the app to its API call by `request_id`.
- 2026-09-26 — The /data browser's endpoints (`/lake/*`, `/tables/*`, `/pipeline/runs`) are this API's first code; `/lake/sources` replaces the contract's draft `/sources`. — Asked by the user; per source it adds files, snapshots, formats, datasets and the last runs.
- 2026-09-26 — The raw-file index is built in memory from the `_manifest.json` of every `dt=` folder (293 today) and rebuilt in the background every 10 minutes, instead of a bucket listing or a Postgres table. — No change in basecast-airflow, and the manifest already carries the URL, sha256 and publish metadata a listing lacks.
- 2026-09-26 — Which datasets exist comes from `public.dataset_registry`, published by basecast-airflow (`basecast registry` and every process run); source names, publishers and schedules shown on /data live in `basecast_get_data/data/sources.yaml`. — Cross-repo: airflow owns the datasets; names and publishers are presentation.
- 2026-09-26 — Only `raw/`, `parquet/` and `derived/` are browsable; any other key (`backups/`, `_logs/`, `_runs/`, `_tmp/`) is refused. — `backups/` holds Postgres dumps, app password hashes included.
- 2026-09-26 — Rows go in offset/limit blocks (limit up to 1,000, window of 100,000 rows), `with_summary=true` adds the total, filters are `filter=column:op:value`. Postgres counts exactly within 6 s and then falls back to the `pg_class` estimate (`total_estimated`); BigQuery reads unfiltered, unsorted blocks with `tabledata.list` and caps every query with `maximum_bytes_billed` (2 GB). — The Fundsys CNPJ grid's contract; plain browsing runs no BigQuery query.
- 2026-09-26 — Raw spreadsheets and delimited text are served positionally (column letters, no header guessing); Parquet and JSON keep their names and types. — The raw view shows what the source published; the processed tables are where headers get interpreted.
- 2026-09-26 — Postgres sessions run with `synchronize_seqscans=off` and read-only transactions; unsorted blocks follow the table key from the registry when there is one. — Offset pagination over a plain sequential scan is only stable if every scan starts at the first page.
- 2026-09-26 — Cloud Run: 2 GiB of memory, Postgres through `--add-cloudsql-instances` (unix socket, psycopg) and `PG_PASSWORD` from Secret Manager; production settings are code defaults, so ENV_YAML does not change. — Spreadsheet previews parse whole sheets. Not verified yet that connector enforcement accepts Cloud Run's built-in socket.
- 2026-09-26 — `/lake/object/url` signs V4 URLs when the service account can (signBlob on itself); otherwise it returns null and the app streams `/lake/object/content` with HTTP Range. — Signing needs an IAM binding and bucket CORS that are not granted yet.
- 2026-09-26 — `get-data-run` holds `roles/iam.serviceAccountTokenCreator` on itself (signBlob), and the lake bucket's CORS allows GET/HEAD from https://basecast.pbrenner.com and http://localhost:3000, exposing Content-Range, Accept-Ranges and Content-Disposition. Download links sign with `response-content-disposition: attachment`. — Applied by hand with gcloud (asked by the user); PDFs and downloads then go from the bucket to the browser without passing through Vercel. Supersedes the "not granted yet" part of the signed-URL line above.
- 2026-09-26 — Verified: Cloud Run's built-in Cloud SQL socket passes the instance's connector enforcement (the first revision reads Postgres). The first deploy reported "already exists" after creating the service itself; the revision was healthy. — Clears the "not verified" of the Cloud Run line above.
- 2026-09-26 — Contract v2 (data-contract.md §1–§5 rewritten): accounts keyed by `account_id` = PUCT `ccn_no`, the EIA id as `eia_utility_id`; `first_deficit_year`, `deficit_mw_p50_next_3y`, `generation_added_mw`, `region_type=county|utility`, `load_zones[]` and `is_base_partner` leave the contract, and `parent_utility_id` becomes `gt`. — The universe is PUCT's; the dropped fields have no public source (marts-proposal §3.1, §5.1), and the partner field waits for the reveal (A-M8).
- 2026-09-26 — `meta` v2: `model_version` replaces `model_run_id` (the app never read it), plus `verified` and `caveats`. Each caveat comes as `{code, label, text}` from one catalog (`schemas/caveats.py`, also `GET /caveats`), with no number a rebuild can move. Rows keep their own `verified` and `simulated`. — openapi-typescript generates types only, so a text in openapi.json would not reach the screen; the app asked for row-level flags to put each badge next to its number.
- 2026-09-26 — Screen values that are not rows (legend breaks, weights, backtest dates, variants) go in `data`, not `meta`; the marts carry them in a new `mart_meta` (mart, key, value jsonb). — Keeps `Meta` one type, and one place for build-level values instead of repeated columns.
- 2026-09-26 — Errors: 503 `{"detail": "mart_not_built", "mart": "<name>"}` (schema `MartNotBuilt`, declared on every product endpoint), 404 `{"detail": "not_found"}` for any unknown id including a held-out account, 422 `{"detail": "invalid_as_of", "as_of_dates": [...]}` on the backtest. — The app shows the 503 as an empty state; the single 404 keeps the validation lock.
- 2026-09-26 — Product endpoints build their responses in Polars from mart-shaped frames (`products/store.py`); until C-2 the frames are fixtures (`data/fixtures/<mart>.json`, same names and columns as the marts, from `scripts/make_contract_fixtures.py`) with fictional accounts `FX001…`. — The same code serves fixtures now and marts later, and no held-out account can reach a fixture.
- 2026-09-26 — Peak forecast rows carry `band_kind` (`p10_p90` | `allocation_range` | null), and zones exist only for the default variant in P0 (`variants[].regions`, `available`). — Session A: X11's zone bands are the spread across candidate shares, not a P10–P90, and the scripts allocate the default variant only.
- 2026-09-26 — The API computes backtest scores from the cells: `scores` by era and source, and `comparisons` pairing basecast with each official source on the same (as_of, target_year). - 2026-09-26 — `/accounts/{id}/events` pages with `offset`/`limit`, not `page`; `rank_scope=within_type` only changes the order, and every item carries both `rank` and `rank_within_type`; `/accounts/export.csv` streams the list's rows as `text/csv` with the signals flattened. — Same paging as `/pipeline/runs`; the app shows either rank without a second call.
- 2026-09-26 — Product resources switch from fixtures to marts by group (`accounts`, `explorer`, `forecast`, `backtest`): `DATA_MODE=marts` reads every mart, and with `DATA_MODE=fixtures` the groups in `MARTS_LIVE` do; the production default of `MARTS_LIVE` lives in `config.py`, so going live is a reviewed push, not an edit of the `ENV_YAML` secret (which sets `DATA_MODE=fixtures`). — The monitor asked to switch endpoint by endpoint as session A publishes checked marts; a response that read any fixture still says `simulated` and carries the `fixture` caveat.
- 2026-09-26 — A mart is loaded whole into memory and reloaded only when its row count, `built_at`, `model_version` or `as_of` change (checked every 10 minutes); a mart missing, or missing a column its fixture has (less provenance and recomputed ranks), answers 503 `mart_not_built`. — Same background pattern as the lake index; a drifted mart fails loudly at load time instead of as a 500 inside an endpoint.
